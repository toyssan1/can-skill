## Core ideas

- Two bus states: **dominant** (logic 0) and **recessive** (logic 1). Any node driving dominant overrides every node sending recessive (wired-AND). Everything else in CAN follows from this.
- No addresses. A frame carries an **identifier** that names the content and sets the priority. Every node sees every frame and filters by ID.
- No clock wire. Encoding is NRZ; receivers synchronise on the start-of-frame edge and resynchronise on later recessive-to-dominant edges. Bit stuffing guarantees enough edges.
- Every transmitter reads back each bit it sends. That one mechanism gives arbitration, bit-error detection and acknowledgement.
- Standards: ISO 11898-1 (data link, includes CAN FD since 2015 and CAN XL since 2024), ISO 11898-2 (high-speed physical layer). "CAN 2.0A" = 11-bit IDs, "CAN 2.0B" = 11- and 29-bit IDs.

## Classical frame format

Base (11-bit ID) data frame, in wire order:

| Field | Bits | Notes |
|---|---|---|
| SOF | 1 | dominant; all nodes hard-synchronise here |
| Identifier | 11 | MSB first |
| RTR | 1 | dominant = data frame, recessive = remote frame |
| IDE | 1 | dominant = base format |
| r0 | 1 | reserved, dominant (this slot is FDF in CAN FD) |
| DLC | 4 | 0-8 bytes. Values 9-15 are legal and mean 8 |
| Data | 0-64 | 0-8 bytes, each MSB first |
| CRC | 15 | polynomial 0x4599, computed over SOF through data, before stuffing |
| CRC delimiter | 1 | recessive |
| ACK slot | 1 | transmitter sends recessive; any node that received a valid frame drives dominant |
| ACK delimiter | 1 | recessive |
| EOF | 7 | recessive |
| Intermission | 3 | recessive, then the bus is idle |

Extended (29-bit ID) frame: SOF, ID bits 28-18 (11), **SRR** (recessive), **IDE** (recessive), ID bits 17-0 (18), RTR, r1, r0, DLC, then as above.

Other frame kinds:
- **Remote frame**: RTR recessive, no data field. Asks another node to send the data frame with that ID. Rare today; J1939 and CAN FD do not use it. In candump it shows as `123#R`.
- **Error frame**: 6 identical bits (the error flag, a deliberate stuffing violation) plus 8 recessive delimiter bits. Not a frame with an ID. An error-active node sends 6 dominant bits, which destroys the frame in progress for everyone, and the transmitter retries.
- **Overload frame**: same shape as an error frame, delays the next frame. Essentially never generated by modern controllers.

Frame length without stuffing, including the 3-bit intermission: base `47 + 8n` bits, extended `67 + 8n` bits (n = data bytes). Worst case with stuffing for 8 bytes: **135 bits base, 160 bits extended**.

## Arbitration

Nodes that start in the same bit slot send their IDs simultaneously. Each compares what it sends with what it reads. A node that sends recessive and reads dominant has lost: it stops driving at once and becomes a receiver. The winner's frame is undamaged, so no time is wasted (CSMA/CR).

Consequences:
- **Lower ID value = higher priority.** ID 0x000 beats everything.
- IDs must be unique per transmitter. Two nodes sending the same ID with different data collide after arbitration and produce bit errors that look like a broken bus. This is exactly what happens when you inject an ID that an ECU already transmits.
- A base frame beats an extended frame whose first 11 bits match (dominant RTR/IDE against recessive SRR/IDE).
- A data frame beats a remote frame of the same ID.
- All nodes must see the same bit before the sample point, so the round-trip propagation delay must fit in the bit time. This is why bus length shrinks as bitrate rises, and why the CAN FD arbitration phase stays at 1 Mbit/s or less.
- A low-priority ID can be starved by heavy high-priority traffic. A controller TX FIFO sends in queue order, not ID order, which can cause priority inversion.

## Bit stuffing

After 5 consecutive bits of the same level the transmitter inserts one bit of the opposite level; receivers remove it. It applies from SOF to the end of the CRC sequence. The CRC delimiter, ACK field and EOF are not stuffed. The stuff bit counts toward the next run, which gives the worst case of one stuff bit per four data bits.

Six identical bits inside the stuffed region is a **stuff error**. Frame length therefore depends on the data, so bus-load and period measurements have a little jitter.

## Error detection

| Error | Seen by | Condition |
|---|---|---|
| Bit error | transmitter | read-back differs from the bit sent (except during arbitration and the ACK slot) |
| Stuff error | receivers | six equal bits in the stuffed region |
| CRC error | receivers | computed CRC differs from the received one; the receiver does not ACK |
| Form error | any node | a fixed-format bit (delimiters, EOF) has the wrong level |
| ACK error | transmitter | nobody drove the ACK slot dominant |

Any node that detects an error sends an error flag immediately (after the ACK delimiter for a CRC error). The frame is void for every node and the transmitter retransmits automatically. Most controllers offer a one-shot mode that disables retransmission.

**ACK means "at least one node received this frame correctly", not "the intended recipient got it".** A logger or sniffer in normal mode ACKs everything.

## Error confinement: TEC, REC, bus-off

Each node keeps a transmit error counter (TEC) and a receive error counter (REC).

| Event | Change |
|---|---|
| Transmitter detects an error | TEC + 8 |
| Receiver detects an error | REC + 1 (+ 8 if it was the first to flag it) |
| Frame transmitted successfully | TEC - 1 |
| Frame received successfully | REC - 1 |

| State | Condition | Behaviour |
|---|---|---|
| Error active | TEC <= 127 and REC <= 127 | sends active error flags (6 dominant bits) |
| Error warning | either counter >= 96 | status flag only |
| Error passive | TEC >= 128 or REC >= 128 | sends passive flags (6 recessive bits, invisible to others); must wait 8 extra bit times before transmitting again |
| Bus-off | TEC >= 256 | stops transmitting and stops ACKing entirely |

Bus-off recovery needs 128 occurrences of 11 consecutive recessive bits, and on most controllers also a software request (Linux `restart-ms`, ESP-IDF `twai_initiate_recovery()` or `twai_node_recover()`, STM32 bxCAN `ABOM` bit, MCP2515 recovers by itself). Use a back-off of 100 ms or more: instant auto-restart on a faulty bus floods it again.

## What the error states look like in practice

| Observation | Meaning |
|---|---|
| A single node alone on the bus retransmits one frame forever, sits at TEC = 128 (error passive), never reaches bus-off | No ACK. The rule that stops TEC rising for ACK errors in the error-passive state causes this. Add a second node in normal mode or use loopback/self-test mode |
| Node goes bus-off within milliseconds of the first transmit | Wrong bitrate, CANH/CANL short or swapped, missing termination, or an ID collision with another transmitter |
| Bus was healthy, dies when a new device is connected | The new device is in normal mode at the wrong bitrate and its error flags destroy every frame. Use listen-only mode until the bitrate is known |
| REC climbing, TEC zero | The node receives corrupted frames: noise, marginal termination, sample-point mismatch, or a wrong oscillator setting |
| Errors only on long frames or only in the CAN FD data phase | Clock tolerance or sample-point mismatch; for FD also missing transmitter delay compensation or a transceiver not rated for the data rate |

**Listen-only (silent) mode**: the controller receives but never drives the bus: no ACK, no error flags, no transmission. It still needs the correct bitrate to decode anything. It is the safe default for sniffing. With only a listen-only node and one transmitter on a bench, the transmitter gets no ACK.

## CAN FD

CAN FD keeps arbitration unchanged and changes what follows it: up to 64 data bytes and an optional faster bitrate for the data phase.

Control-field bits after the ID (base format): `RRS` (replaces RTR, always dominant: FD has no remote frames), `IDE`, **`FDF`** (recessive marks an FD frame; this was the reserved r0 bit), `res` (dominant), **`BRS`** (recessive = switch to the data bitrate at this bit's sample point), **`ESI`** (recessive = the transmitter is error passive), then DLC.

DLC to length:

| DLC | 0-8 | 9 | 10 | 11 | 12 | 13 | 14 | 15 |
|---|---|---|---|---|---|---|---|---|
| Bytes | 0-8 | 12 | 16 | 20 | 24 | 32 | 48 | 64 |

Only these lengths exist. A 13-byte payload is sent as 16 bytes with padding, so the receiver needs to know the real length from the protocol above.

Other differences:
- CRC is 17 bits for up to 16 data bytes, 21 bits above that. The CRC field uses fixed stuff bits and is preceded by a 4-bit stuff count (ISO CAN FD).
- The bitrate switches back to nominal at the CRC delimiter. ACK is sent at the nominal rate.
- Typical bitrate pairs: 500k/2M (the common automotive profile), 500k/5M, 1M/5M, 1M/8M. Multi-drop vehicle networks rarely exceed 2 Mbit/s without signal-improvement (SIC) transceivers.
- **Transmitter delay compensation (TDC)**: at 2 Mbit/s and above the transceiver loop delay approaches or exceeds one bit time, so a transmitter cannot check its own bits at the normal sample point. The controller measures the loop delay and checks at a secondary sample point (SSP = measured delay + offset). Missing or wrong TDC shows as transmit errors only in the data phase. Enable it for data rates of 2 Mbit/s and up; the usual offset is the data-phase sample point.
- **ISO vs non-ISO CAN FD**: the original Bosch format (2012) has no stuff count and a different CRC start value. The two are not interoperable; each sees the other's frames as CRC errors. Everything current is ISO. Early controllers and some logger settings offer a "non-ISO" switch (`fd-non-iso on` in Linux). Suspect this when two FD devices at correct bitrates cannot talk.
- **Mixing with classical-only nodes**: a classical controller does not understand a recessive FDF and sends an error flag, destroying every FD frame. FD nodes may send classical frames, so a mixed bus works only if no FD frames are sent while classical-only nodes are awake. ESP32 TWAI (except FD-capable chips such as ESP32-C5), MCP2515, STM32 bxCAN and SJA1000 are classical-only: on an FD bus they must be in listen-only mode, and even then they report errors instead of data for FD frames.

## CAN XL

Third generation, in ISO 11898-1:2024 and the CiA 610 series. Know it exists and what distinguishes it:

- Payload 1 to 2048 bytes.
- An 11-bit **priority ID** used only for arbitration, separate from a 32-bit **acceptance field** used for addressing and filtering.
- **SDT** (8 bits, says what the payload is, like an EtherType) and **VCID** (8 bits, virtual network ID).
- Data phase of 10 Mbit/s and more using SIC XL transceivers that switch to push-pull signalling (PWM-coded between controller and transceiver).
- Can share a bus with CAN FD nodes that implement protocol-exception handling.

Deployment is at an early stage. Hobbyist hardware does not support it; Linux has had `canxl` frame support since kernel 6.x.

## Bus load and frame time

- Time on the wire for one classical frame is about `(47 + 8n) x 1.1 / bitrate` for 11-bit IDs (the 1.1 covers typical stuffing). An 8-byte frame at 500 kbit/s takes about 0.25 ms, so the bus carries roughly 4000 such frames per second at 100 % load.
- Keep average load under about 50-60 % for periodic traffic so that low-priority frames still meet their timing.
- `canbusload can0@500000 -r -t -b -c` measures it on Linux.
